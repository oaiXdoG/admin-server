# 服务发现改造（管理后台）

总规则见 danmu-login `docs/service-discovery.md`，本文是管理后台这一侧的改动清单和验收项。

改造后后台不再读 ZooKeeper：各项目的游戏服用 HTTP 定时上报到后台，后台按 `App Key → 区 ID` 两层 key 保存，「按区自动发现」数据源从这份上报数据里取各区的查询接口地址。后台是一个进程管理所有项目，所有项目的游戏服都上报到同一个地址。

## 1. 删除

| 内容 | 说明 |
| --- | --- |
| `ZoneDiscoveryService` 中的 Curator 客户端、`client()`、`close()` 和读 `/danmu/<appKey>/logic` 的代码 | 改为读上报数据 |
| `ApplicationProperties.zookeeperAddress` 和配置项 `zookeeper.address` | 后台不再连接 ZooKeeper |
| `ErrorCode.ZOOKEEPER_NOT_CONFIGURED(100086)` | 不再使用；admin-front 中没有引用 |

## 2. 新增上报接口

### 2.1 路由

`POST /api/node/report`，不需要登录（不校验 `Authorization`），按签名鉴权。

- 在 `Application` 路由表中注册，解析方式与 `/api/agent/heartbeat` 相同：请求体在进入控制器前已释放，先把请求体的 SHA-256 写入内部请求头（`AgentService.BODY_DIGEST_HEADER` 的做法，覆盖客户端传来的同名头），再解析为 `NodeInfoReportRequest`。
- 请求类 `NodeInfoReportRequest`（`@JsonIgnoreProperties(ignoreUnknown = true)`，不认识的字段忽略，节点新增字段时后台不用先升级）字段：`Integer serverId`、`String instanceId`、`String host`、`Integer port`、`String innerHost`、`Integer gmPort`。

### 2.2 验签

请求头：

| 请求头 | 值 |
| --- | --- |
| `X-Admin-Project` | 项目 App Key |
| `X-Admin-Timestamp` | 毫秒时间戳 |
| `X-Admin-Signature` | `hex(HMAC-SHA256(密钥, 时间戳 + "\n" + hex(SHA256(请求体))))`，小写十六进制 |

规则：

1. 按 `X-Admin-Project` 找项目；找不到 → 拒绝。
2. 取该项目下所有 `type=zone`（按区自动发现）的数据源，逐个解密密钥，任一密钥算出的签名与 `X-Admin-Signature` 相同即通过（用 `MessageDigest.isEqual` 比较）；项目下没有 `zone` 数据源 → 拒绝。
3. `|当前时间 - 时间戳| > 5 分钟` → 拒绝。
4. 签名计算复用 `BusinessClient.sign`、`AgentService.digest`。
5. 拒绝时返回新增错误码 `NODE_REPORT_DENIED(100088, "节点信息上报验签失败")`，打印警告（App Key、serverId、来源 IP、原因），同一 App Key + 来源 IP 每分钟最多打印一次。

### 2.3 参数校验

`serverId > 0`；`host`、`innerHost` 非空；`port`、`gmPort` 在 0～65535；`instanceId` 非空。不合法 → 返回 `INVALID_REQUEST`。

### 2.4 存储：`NodeInfoReportService`

内存表：

```text
ConcurrentHashMap<String appKey, ConcurrentHashMap<Integer serverId, Node>>
Node = { serverId, instanceId, host, port, innerHost, gmPort, reportTime }
```

- 每次收到直接覆盖（不做区 ID 冲突判断，冲突由登录服、回调服拦截）。
- 记录不删除。
- 在线：`当前时间 - reportTime ≤ 30 秒`。
- 后台重启后表为空，游戏服 10 秒内重新上报补齐。
- 后台按单进程部署；以后多实例部署时要改为放 Redis。

## 3. 修改 `ZoneDiscoveryService.zones(appKey, publicNetwork)`

方法签名和返回值 `List<Zone(zoneId, url)>` 不变（`zoneId` 取上报的 `serverId`），`DataSourceService` 不用改：

- 数据来自 `NodeInfoReportService` 中该 App Key 的记录。
- 只返回在线且 `gmPort > 0` 的区。
- `url`：`publicNetwork=false`（连接方式「内网」）为 `http://<innerHost>:<gmPort>`；`publicNetwork=true`（「公网」）为 `http://<host>:<gmPort>`。
- 按区 ID 排序；没有记录返回空列表（调用方仍按原逻辑返回 `ZONE_NOT_AVAILABLE`）。

## 4. 部署

- 上报地址（游戏服 `admin.report-url`）为后台对外地址加 `/api/node/report`，游戏服所在服务器要能访问到。
- 数据源的连接方式（内网/公网）含义不变：后台访问游戏服 GM 接口时用哪个地址。

## 6. 验收项

| # | 场景 | 预期 |
| --- | --- | --- |
| 1 | 后台配置中没有 `zookeeper.address` | 正常启动，「按区自动发现」数据源可用 |
| 2 | 游戏服正确签名上报 | 返回成功；数据源「测试连接」能看到该区 |
| 3 | 签名错误 / 时间戳超过 5 分钟 / App Key 不存在 / 项目没有 zone 数据源 | 返回 `100088`，不保存 |
| 4 | 参数不合法（如 `serverId=0`） | 返回 `INVALID_REQUEST` |
| 5 | 两个项目各自上报 1 区 | 两个项目的数据源各自只看到自己的 1 区 |
| 6 | 同一项目同一区重复上报 | 覆盖，只保留最新内容 |
| 7 | 游戏服停止超过 30 秒 | 数据源中该区消失（不在线），查询该区记为失败 |
| 8 | 游戏服 `gm.secret` 为空 | 不上报，后台看不到该区 |
| 9 | 上报 `gmPort=0` | 该区不出现在可查询列表 |
| 10 | 连接方式「内网」/「公网」 | 查询地址分别为 `innerHost:gmPort`、`host:gmPort` |
| 11 | 后台重启 | 10 秒内各区恢复 |
| 12 | 代码检查 | 后台没有任何 ZooKeeper / Curator 代码；`ErrorCode` 中没有 `100086` |
